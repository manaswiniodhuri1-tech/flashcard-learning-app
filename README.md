# Flashcard Learning App

A beginner-friendly full-stack flashcard study tool built with HTML, CSS, Vanilla JavaScript, Node.js, Express, and Supabase PostgreSQL.

## 1. Overview

Students often reread notes without checking what they can remember. This application lets a student create question-and-answer cards, organize them by subject, search and filter them, flip cards during a study session, and mark them as known or needing review.

### Objectives
- Practise active recall with question/answer cards.
- Organize cards by subject and difficulty.
- Track known cards and cards that need review.
- Store cards persistently in PostgreSQL through Supabase.

### Target users and roles
The MVP is a single shared study space intended for a local college-project demonstration. It has no user accounts or roles. Anyone who can reach the locally running application can see and change the shared cards. Do not expose this version publicly with real or private study data.

## 2. Features

- Create, view, edit, and delete flashcards.
- Search questions, answers, and subjects.
- Filter by subject and review status.
- Study cards one at a time and reveal answers.
- Mark cards as known or needing review.
- Summary counts for all, known, and review cards.
- Responsive layout and friendly status/error messages.
- PostgreSQL persistence via the Express API.

## 6. Set up Supabase

1. Sign in to Supabase and create a new project.
2. Choose a project name and a strong database password. Save the database password privately; this app does not need that password directly.
3. Wait until the project is ready.
4. In the Supabase dashboard, open **SQL Editor** and choose a new query.
5. Open `database/schema.sql` in VS Code, copy the complete contents, paste into the SQL Editor, and run it.
6. Open **Table Editor** and verify that the `flashcards` table exists with `id`, `question`, `answer`, `category`, `difficulty`, `known`, `created_at`, and `updated_at`.
7. Open **Project Settings → API Keys** (the exact menu label can vary). Copy the project URL and a server-side secret key. Use a server-only secret key, not a publishable/anon key, for this MVP's backend design.

The schema enables Row Level Security and intentionally creates no public policies. The backend uses the server-side secret key, which bypasses RLS. Therefore, the secret must remain on the server and the API must not be exposed publicly without authentication and authorization.

## 7. Configure environment variables

Copy `backend/.env.example` to `backend/.env` and replace the placeholders:

```dotenv
PORT=3000
NODE_ENV=development
SUPABASE_URL=https://YOUR-PROJECT-REF.supabase.co
SUPABASE_SECRET_KEY=your_actual_server_side_secret_key
```

- `PORT`: local web-server port.
- `NODE_ENV`: development mode for local work.
- `SUPABASE_URL`: URL shown in your Supabase project settings.
- `SUPABASE_SECRET_KEY`: server-only secret key from Supabase.

Never paste a real key into `frontend/app.js`, HTML, CSS, GitHub, screenshots, or reports. The `.env` file is ignored by Git. `.env.example` contains placeholders only and is safe to commit. If a secret is exposed, rotate it immediately in Supabase.

## 8. Install and run

Open the project root folder in VS Code. Open **Terminal → New Terminal**, then run:

```bash
cd backend
npm install
npm run check
npm start
```

Expected startup output:

```text
Flashcard Learning App running at http://localhost:3000
Health check: http://localhost:3000/api/health
```

Leave this terminal running. Open http://localhost:3000 in your browser. Do not open `index.html` directly as a file, because the page must call the Express API.

Check the health endpoint at http://localhost:3000/api/health. It should return JSON containing `"status":"ok"`. This only confirms Express is running; it does not prove that Supabase credentials are correct. Create a card in the UI to verify the database connection.

## 9. Architecture

1. The browser renders the files in `frontend/`.
2. `frontend/app.js` sends JSON requests with `fetch()` to `/api/cards`.
3. Express validates each request in `backend/routes/cards.js`.
4. `backend/supabase.js` creates the Supabase client using server environment variables.
5. Supabase PostgreSQL stores flashcards persistently.
6. The backend returns JSON to the browser.

## 10. API reference

All successful responses use JSON. Card fields are `id`, `question`, `answer`, `category`, `difficulty`, `known`, `created_at`, and `updated_at`.

| Method | Path | Purpose | Body / parameters | Success |
|---|---|---|---|---|
| GET | `/api/health` | Check Express status | None | `200 { status, service, timestamp }` |
| GET | `/api/cards` | List cards, newest first | None | `200 { data: [...] }` |
| POST | `/api/cards` | Create a card | `question`, `answer`, optional `category`, `difficulty` | `201 { data: card }` |
| PATCH | `/api/cards/:id` | Update card fields or known status | Any of `question`, `answer`, `category`, `difficulty`, `known` | `200 { data: card }` |
| DELETE | `/api/cards/:id` | Delete a card | UUID in path | `200 { data: { id, deleted: true } }` |

No endpoint has user authentication in this local demonstration. Do not deploy it publicly as-is. Validation failures return `400`, invalid UUIDs return `400`, missing cards return `404`, unknown API paths return `404`, and unexpected failures return a generic `500` message.

Example request body for `POST /api/cards`:

```json
{
  "question": "What does HTML stand for?",
  "answer": "HyperText Markup Language",
  "category": "Web development",
  "difficulty": "Easy"
}
```

## 11. Sample usage

1. Click **Add a card**.
2. Enter a question, answer, subject, and difficulty.
3. Save the card and confirm it appears in the list.
4. Use the search box or subject/status filters.
5. Click **Study** on one card or **Start study session** for all cards.
6. Reveal the answer and mark it as known or needing practice.
7. Edit or delete a card if required.
8. Refresh the page. Cards should still exist because they are stored in PostgreSQL.

No seeded demo cards are inserted automatically; add your own study content.

## 12. Testing

### Manual checklist

- Health endpoint returns status `ok`.
- Creating a valid card adds it to the list and database.
- Refreshing the page preserves cards.
- Empty question or answer is rejected.
- A question longer than 500 characters is rejected by the backend.
- An answer longer than 1,000 characters is rejected by the backend.
- Invalid difficulty is rejected.
- Search finds words in the question, answer, and subject.
- Subject and known/review filters work.
- Edit changes the saved card.
- Marking known updates the summary counts.
- Delete requires confirmation and removes the card.
- An invalid UUID returns `400`; a valid but missing UUID returns `404`.
- Narrow the browser window to verify responsive layout.
- Temporarily stop the backend and refresh: a connection error should be shown.

### Syntax check

From `backend/` run:

```bash
npm run check
```

This checks the syntax of the included backend JavaScript files. It does not test your remote Supabase connection or browser interactions.

## 13. Troubleshooting

- **`npm` is not recognized:** install Node.js LTS, close and reopen VS Code, then run `node --version` and `npm --version`.
- **Port 3000 is busy:** change `PORT=3001` in `backend/.env` and open `http://localhost:3001`.
- **Supabase URL/key error:** check for typos and ensure `.env` is inside `backend/`, beside `server.js`.
- **Table does not exist:** run all of `database/schema.sql` in the Supabase SQL Editor.
- **401/403 or permission error:** check that the server-side secret key is correct and belongs to the same project as `SUPABASE_URL`. Never replace it with a frontend key in browser code.
- **Page opens but cards do not load:** check the backend terminal and `/api/health`, then verify Supabase configuration and the table name.
- **Changes are not visible:** refresh the browser; inspect the terminal for API errors.
- **Blank or broken page:** confirm the server is running and you opened the URL rather than double-clicking `index.html`.

## 14. Security notes and limitations

- This MVP has no login, per-user ownership, or roles. Cards are shared by anyone who can access this local app.
- The server-side Supabase secret bypasses RLS. Backend routes must remain trusted and must be secured before any public deployment.
- Add authentication, user ownership checks, rate limiting, and stricter production configuration before deployment.
- Do not use real personal or confidential data in a public demonstration.
- This project does not include spaced-repetition scheduling, import/export, or automated browser tests.
